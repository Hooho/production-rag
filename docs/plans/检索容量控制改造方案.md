# 检索容量控制改造方案

日期：2026-11-15

状态：方案已整理，尚未实施。

## 目标

按 token 预算选择资料时，取消前面各阶段用于控制正常容量的固定段数、关系数截断，避免最终预算还有余量，相关证据却已经被提前丢弃。

最终交付顺序统一为：

1. 优先交付通过相关度筛选的图关系。
2. 剩余预算交付原文。关键词、向量和图检索找到的原文统一重排、公平竞争。
3. 还有余额再做父子扩展，不为扩展预留容量。

本次仅针对按 token 选择资料的模式；按段数模式保持现有行为。

## 当前限制

当前代码中存在以下独立限制。下列数值为代码默认值，历史评测的实际取值以运行配置快照为准。

| 阶段                   | 当前限制                             |
| ---------------------- | ------------------------------------ |
| 普通原文候选进入重排   | 融合排序后取前 12 段                 |
| 图关系进入关系重排     | 最多 100 条                          |
| 关系重排后保留         | 最多 30 条                           |
| 图独有原文进入原文重排 | 最多 15 片                           |
| 最终图资料保障         | 按图检索保底比例安排关系及图独有原文 |

因此，只提高最终原文 token 预算，并不能恢复前面被数量上限截掉的证据。

相关实现位于 `app/tools/search.py`、`app/graph/retrieve.py`、`app/graph/relation_retrieval.py` 和 `app/runtime_config.py`。

## 容量与相关度分开控制

- token 预算决定最多保留多少内容。
- 相关度门槛决定内容是否值得保留，不能为了填满预算降低门槛。
- 候选预算与最终交付预算分开。候选只是用于筛选，不占用最终交付容量。
- 查询超时、分页次数、最大处理数量等异常保护仍然保留；触发时必须在日志中明确记录，不能伪装成正常预算截断。

## 普通原文候选

关键词、向量召回后，合并重复分片，按现有融合排名组织候选。将进入重排前的固定段数限制替换为候选原文 token 预算。

底层召回也需要同步调整，避免上游仍只返回少量结果。优先采用有界分页补取；去重后的候选容量不足时继续补取，直到达到容量、结果耗尽或触发执行保护。

候选容量应大于最终交付容量，以容纳重排淘汰和重复内容。候选预算倍率先以 3 倍作为验证起点，最终数值根据命中率、耗时和重排成本确定，不视为已确认的最优值。

## 图关系候选与交付

图关系候选按实际送入关系重排的文本表示计算 token，使用独立的关系候选预算。原文长度不用于估算关系文本容量。

按 token 模式下，关系重排前的候选数上限、重排后固定保留 30 条等正常容量限制，改为对应阶段的 token 容量控制。实体内和全局候选配额等可能提前丢弃关系的规则也需一并检查，不能留下隐性的条数瓶颈。

关系经过统一的关系重排及相关度过滤后，去重并按关系重排顺序优先装入最终总预算。所谓关系全部交付，是尽可能交付全部合格关系，仍不能超过最终总预算。某条装不下时跳过，继续尝试后续关系。

关系候选预算的具体数值或倍率在实施时明确，并通过评测验证；不直接套用原文候选预算，因为两者的表示长度及处理成本不同。

最终交付的关系应保留可追溯的出处标识。关系只代表抽取后的紧凑信息，不能在展示和回答中冒充完整原文。

## 图原文候选

图独有分片单独按图原文候选 token 预算进入原文重排，不与关键词、向量候选争夺重排前的融合排名。

原因是普通检索可能得到多个检索词、多个召回路的融合加分，图独有分片只有图一路贡献，不能以这个分数决定它是否有资格进入重排。

进入原文重排前，三路候选按分片标识去重，同一分片只重排一次，同时保留全部召回来源用于诊断。图独有候选与普通候选各自的容量需明确配置和记录，避免比较时一组无意获得更大的总处理预算。

## 原文统一竞争

全部原文候选使用同一个重排模型、同一种评分输入格式和相关度门槛。

重排通过后，不再区分召回来源，按重排分数竞争关系交付后剩余的 token 容量。取消图独有原文在最终交付阶段的保底。

图关系和原文使用不同的评分对象，不直接混排分数。关系通过优先交付规则安排容量，原文通过统一重排安排容量。

现有图检索保底比例在 token 模式下退出容量分配逻辑，替换为“关系优先、原文统一竞争”的规则。配置界面、运行快照和报告需要同步表达新规则；历史报告继续按当时的配置解释。

## 最终总预算

最终总预算覆盖实际交付的图关系、原文以及父子扩展内容。当前名为原文预算的配置和说明需要同步明确其覆盖范围，避免用户误以为关系免费、不占容量。

统一使用现有 token 估算方法，对实际交付文本计量。原文去重后只计算新增内容；同一出处既支撑关系又提供原文时，关系文本和原文是两份实际交付内容，应分别计量。

逐条装入时，某条内容超出剩余容量，不立即终止整个流程，而是跳过该条，继续尝试后续内容。不得因父块太长而丢弃本来能装入的命中子块。

例如总预算为 12,000 token：合格关系使用 2,000，原文最多使用剩余 10,000；关系只使用 500，原文就可使用剩余 11,500，不再固定预留 50%。

## 父子扩展

父子扩展保留，但不预留固定预算。

先完成关系和命中原文的装入，再对已入选子块补充父块或邻近上下文。扩展只使用剩余容量，不挤掉已入选资料。

同一父块下的多个命中统一处理，重叠部分只计一次。没有剩余容量时不扩展，这是允许的正常结果，不要求每道题都使用父子扩展。

## 日志与报告

每个容量筛选阶段至少记录：

- 配置预算、输入及保留的 token 数、候选数量。
- 截断原因：候选容量不足、低于相关度门槛、最终容量不足、执行保护触发。
- 普通召回、图独有候选各自的去向，以及统一重排后的排名和分数。
- 最终关系、命中原文、父子扩展分别占用的 token，以及剩余容量。

原有“超过关系保留上限”“没进前 N 段”等说明，在新模式下改为实际的容量或保护原因；历史记录保持兼容。

## 验证方式

先重跑批次 `20261115-084753-0c16a1` 对应的 9 道题，使用同一语料、题目、重排模型和最终总预算，对比普通检索与加入图检索的结果。

重点检查：

1. 原先排在第 19、23、44 名等被固定候选池截掉的证据，是否获得重排机会。
2. 已召回但因关系数量上限丢弃的证据，是否进入后续筛选及交付。
3. 图独有原文能否进入统一重排，且最终没有来源保底干预排序。
4. 总 token 不超预算，重复内容不重复计量，装不下的条目不会阻止后续条目入选。
5. 直接证据装满时允许不扩展；有余额时扩展正确计量。
6. 对比计分项命中、完整通过率、最终资料量、耗时和重排处理量，避免只看总分。

公平比较时除最终容量外，还应报告候选处理容量与执行成本。可追加总候选处理容量一致的对照，区分图检索本身的增益与增加候选处理量带来的增益。

## 实施边界

本方案不改变图谱抽取方式、分片策略、关系评分目标或评测题目。先完成容量逻辑调整和诊断，再根据评测决定是否调整候选倍率及扩展策略。

实施功能时补充必要的预算边界、去重和排序验证。每完成一个功能单独提交，并根据实际改动的服务提供 `docker-compose` 更新命令。
