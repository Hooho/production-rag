01　文档解析与多模态

检索的上限由入库内容决定。OCR 漏字、表格错列、标题层级错误，会把正确事实变成错误或不可检索的资料。

项目实现方式优点 / 设计动机缺点 / 适用边界依据
PROD-RAGUnstructured hi_res；中英 Tesseract OCR；表格结构识别；Excel/CSV 专用解析；页码与元素元数据。已有版面/OCR能力，解析统计与中间结果便于排错。表格模型异常会关闭该进程的表格结构识别；复杂图表未见独立视觉索引。源码
FastGPT支持多种文档导入；搜索侧可使用图片描述或图片向量。图文有多种进入检索的路径。依赖视觉与向量模型配置；支持图片不等于能精确读图表。[1]
WeKnora多模态解析、Office 解析与企业数据源接入。覆盖资料形式和同步来源更广。解析链路和可选服务增加运维与质量验证负担。[2]
QAnythingPDF/OCR 等独立服务；v2 列出表格、图片处理。本地组件可替换，适合离线知识问答。不同解析器输出需单独验收；不能用格式支持数代替质量。[3]
MaxKB文档上传和在线文档抓取；支持多模态输入输出。资料导入和业务接入方便。多模态对话并不能证明原生图片检索质量；解析细节本次未充分核验。[4]
Dify文档提取与知识处理 Pipeline，可组合处理组件。解析流程可作为可复用资产。质量取决于实际选用的处理器与插件。[10]
RAGFlow强调复杂文档理解、模板处理和可检查的分块。复杂 PDF、扫描件、表格值得作为重点对照。解析通常比纯文本提取昂贵；仍需用同一份文档验证。[7]
GraphRAG在文本输入上抽取知识；不应当作完整 OCR 平台。专注知识结构构建，便于接入外部解析链路。前置解析需要自行准备；错误会传播到图与摘要。[9]
对你的项目：你的解析并非基础纯文本方案。下一步应比较表格关系、阅读顺序、OCR 数值与限定词是否保真。

用这个问题检验：同一份扫描表格，检查“每人/每月/含税/例外”是否随数值一起被正确保留。

02　分块、父子结构与上下文

小块更容易匹配单一事实，大块更容易保留条件。父子检索把检索粒度和回答粒度分开，但会增加上下文与噪声。

项目实现方式优点 / 设计动机缺点 / 适用边界依据
PROD-RAG按标题、段落切分；默认 800 字与 120 字重叠；同节邻块扩展，半径 3、最大 2400 字；表格按行。易观察和调参，限制跨小节串入内容。邻块扩展不是预建层级父块；独立的例外条款可能位于另一节。默认字数仍是经验值。源码
FastGPT可分段、QA 导入及手工编辑；一条内容可建多个向量索引。检索入口可变短，同时保留完整答案块。人工维护与额外索引有成本；不能等同你的邻块扩展。[1]
WeKnora官方列出父子分块，并支持分块编辑和版本回滚。小块匹配、大块回答，兼顾维护。父子边界选择仍可能遗漏跨父块条件。[2]
QAnythingv2 支持解析分块可视化和编辑。可直接修正坏分块。本次未核验统一父子层级策略，不能推断没有。[3]
MaxKB自动文本分段与知识库管理。配置和维护门槛较低。具体层级分块策略本次未充分核验。[4]
Dify父子模式：子块匹配后返回父块，可用段落或完整文档作为父块。明确分离两种粒度。整文档父块可能超预算，且引入大量不相关文本。[6]
RAGFlow模板分块，允许检查和干预；知识编译还可形成树等组织结构。按资料类型调整结构。模板选择与知识编译带来配置和计算代价。[7]
GraphRAG文本单元加实体、关系、社区报告；查询按模式组装上下文。不限于相邻文本，能组织跨文档关系。抽取摘要有信息损失；图结构不能替代精确原文证据。[8]
对你的项目：先测分块是否切掉限定条件，再决定调整字数、建立明确父块，还是补跨节检索。

用这个问题检验：“允许退货”与“定制品除外”若位于不同章节，扩展附近文本未必能救回例外。

03　索引、向量模型与知识组织

索引决定哪些内容能成为检索入口。内容前缀、多向量、生成问题和图结构解决不同的匹配问题。

项目实现方式优点 / 设计动机缺点 / 适用边界依据
PROD-RAGMilvus 密集向量与 BM25 稀疏索引；可生成块上下文并前置到索引文本；向量复用与版本管理。保留原文同时改善脱离全文后的匹配；减少重复计算。生成前缀可能引入错误或占用模型输入；功能依赖实际模式/开关。源码
FastGPT多向量映射到同一内容，命中后合并；数据库引擎可替换。长内容可用多个短入口召回。索引放大、去重和人工维护成本上升。[1]
WeKnora可替换存储后端，结合文本检索与可选知识图谱。组织方式与部署选择更多。不同后端的过滤、排序行为需一致性测试。[2]
QAnythingBCEmbedding 双语语义模型与重排；v2 支持混合搜索。中英文语义匹配值得对照。公开模型榜单不等于你的领域效果；版本与实际模型需固定。[3]
MaxKBPostgreSQL + pgvector；文档自动向量化。基础数据与向量部署栈较集中。数据库集中也意味着共享资源竞争；未核验其全套索引策略。[4]
Dify索引与检索策略可配置，支持模型生态。可以快速对照不同模型和处理流程。自由度高，不存在通用最优默认配置。[5]
RAGFlow常规检索结合知识编译产物，如图、Wiki、树。为复杂查询增加不同粒度知识入口。编译和更新代价较高，衍生知识需追溯原文。[7]
GraphRAGLLM 抽取实体、关系，构建社区报告。给关系与全局主题提供结构化入口。索引耗费模型调用；实体消歧和错误抽取会影响质量。[8]
对你的项目：你已经有上下文索引，不应直接认定缺高级索引。多向量和图结构需要分别证明对目标题型有增益。

用这个问题检验：“该公司”补成真实公司名可改善检索；错误补成另一家公司会污染索引。

04　查询理解、改写与路由

用户问题往往省略对象、条件或上下文。改写把对话还原成独立查询，路由避免把数据库查询硬塞进文档检索。

项目实现方式优点 / 设计动机缺点 / 适用边界依据
PROD-RAG单 Agent + LangGraph；意图、改写、记忆、知识/订单/业务 Tool 路由。结构固定，处理过程可逐步查看。意图误判或改写丢限定词可能让后续检索方向错误。源码
FastGPT问题优化，工作流分支与多库搜索。方便配置指代消除、分类和业务分流。配置分支越多，维护与调试越复杂。[1]
WeKnoraRAG 与多步 Agent 共用知识库。复杂任务可选择检索与阅读工具。Agent 决策可能波动，并引入额外模型往返。[2]
QAnything支持文件问答、Bot、仅检索等模式。围绕文档问答的使用路径较直接。精确查询改写流程本次未核验，不推断缺失。[3]
MaxKB工作流、函数与 MCP 工具编排。适合把业务分支显式配置出来。是否正确路由仍需用真实任务测试。[4]
DifyWorkflow/Chatflow/Agent，可连接模型与工具。应用编排弹性高。可搭建不等于默认开启可靠的查询理解。[10]
RAGFlowAgentic Retrieval 可分析复杂问题并拆解。可针对多证据问题生成子查询。拆解错误、重复搜索和多步延迟需控制。[7]
GraphRAGLocal / Global / DRIFT 等查询模式。根据实体与全局问题选择不同检索逻辑。业务意图路由仍需外部应用承担。[8]
对你的项目：改写不能只看语言更通顺，应测试人物、日期、否定和约束是否保留。

用这个问题检验：“那去年买的呢？”必须还原商品对象和年份，不能只检索“去年购买”。

05　召回与融合

语义搜索补同义表达，关键词搜索补编号和专有名词；融合把尺度不同的结果合并。召回漏掉证据，重排无法凭空补回。

项目实现方式优点 / 设计动机缺点 / 适用边界依据
PROD-RAG每个查询向量 Top12、BM25 Top30；RRF 汇总；默认仅前12进入重排，可做 sum/best 消融。不同信号互补，诊断可看每路贡献。扩大重排池不会扩大每路原始召回；多条相似改写累加可能重复奖励同一候选。源码
FastGPT语义/全文/混合及图片路径，RRF 合并。多路匹配覆盖更广。原始召回与重排的最终融合需按版本配置确认，不能假定与本项目相同。[1]
WeKnora关键词+向量混合，支持重排；API 存在不同层次搜索入口。检索可独立供外部应用使用。调用哪个端点及是否启用重排会改变结果，不能用接口名称代替链路确认。[2]
QAnythingv2 明确支持 BM25+embedding。并非只有纯向量召回。融合的具体权重/公式本次未核验。[3]
MaxKBRAG 检索、分段选择和业务编排。易通过应用配置调试。v2 当前具体融合算法本次未充分核验。[4]
Dify向量、全文、混合；混合支持加权分数或重排策略。可以按语义/精确词需求调整。权重和分数尺度依赖配置；需验证筛选后完整证据覆盖。[5]
RAGFlow多路召回与融合重排。召回策略可面向复杂知识资料。多路增加计算与噪声，优势必须按场景测。[7]
GraphRAG局部结合图与原文；全局基于社区报告；也有基础向量查询。跳出仅相似片段，覆盖关系与全局信息。全局检索不以逐字原文命中为唯一目标。[8]
对你的项目：你应把每路召回深度、融合候选池和最终返回数分开调参。目前三个环节不是同一个 TopK。

用这个问题检验：错误码 E1048 先看关键词召回；“无法连接数据库”更依赖语义召回。

06　重排、相关性阈值与失败回退

重排细看问题与候选的关系，比单向量相似度更有表达力；阈值可减少无关资料，但可能错删可回答证据。

项目实现方式优点 / 设计动机缺点 / 适用边界依据
PROD-RAG本地交叉编码器；logit 经 sigmoid；直接替换 RRF 排序；默认阈值0.85；失败退回RRF且关闭相关性过滤。排序责任明确，可定位重排与阈值丢证据。仅本地 embedding 模式实际调用重排；0.85不是85%正确率；故障时质量保护变弱。源码
FastGPT可启用重排并按相关分过滤，官方还描述与其他排名合并。保留多路信号，参数可调。多信号可能稀释重排意见；是否有收益需做融合消融。[1]
WeKnora官方明确支持 rerank。有第二阶段相关性判断。本次未核验完整评分公式，不引用 Issue 中的具体权重为确定实现。[2]
QAnything两阶段，BCEmbedding 配套 reranker。模型组合便于离线对照。模型排行榜不能证明面对你的难负例更好。[3]
MaxKB具体重排模型、融合及异常回退本次未充分核验。可通过实际配置与源码继续确认。不能仅凭平台定位判断存在或不存在。[4]
Dify检索配置支持 rerank，TopK 与分数过滤。便于更换模型和调权重。模型调用、候选数量与阈值共同影响延迟和漏检。[5]
RAGFlow多路召回配融合重排。兼顾多个检索信号。具体分数与回退需要固定版本后核验。[7]
GraphRAG局部/全局查询核心是上下文组织与聚合。覆盖关系与摘要推理。不能视为在所有路径上统一加交叉编码器重排。[8]
对你的项目：阈值需要按难负例与留出集校准。重排服务异常应单独记录误答率，而不仅是请求成功率。

用这个问题检验：证据说“部分产品可退”，与“所有产品可退”的问题高度相关，却不足以支持肯定答案。

07　多证据、充分性与多步检索

相关不等于充分。多步骤查询为缺失子问题继续寻找证据，但带来累积错误与可变延迟。

项目实现方式优点 / 设计动机缺点 / 适用边界依据
PROD-RAG充分/部分/不足三级判断；最多补检索一次；不足清空来源、部分回答；判断依赖聊天模型模式。有限循环、可控时延，可解释缺少什么。复杂任务可能需要多于一次；判断非法值当前默认 sufficient，存在放行风险。源码
FastGPT工作流可串接分类、搜索与模型处理。可显式搭建检查与补搜。可搭建不等于所有应用默认具备充分性检查。[11]
WeKnora多步 Agent 和知识阅读工具。跨文档证据收集更灵活。停止条件和工具选择需要验证。[2]
QAnything两阶段检索问答为主要已确认机制。普通文档问题路径直接。专门多步证据补全本次未核验。[3]
MaxKBAgentic Workflow 可编排工具和分支。可以围绕业务问题搭建补搜流程。默认链路是否如此需确认。[4]
Dify工作流与 Agent 可组织多次检索。适合把子问题和证据状态显式表达。流程建设与模型判断成本增加。[10]
RAGFlow官方描述分析、拆解、多轮检索和验证，并提供思考深度。复杂多证据问题值得测试。深度越大，模型往返和延迟通常越多。[7]
GraphRAGDRIFT 利用社区信息拓展局部查询；Global 聚合社区报告。关系与全局问题有专门方法。多个摘要可能共享相同原始证据，不能当独立事实验证。[8]
对你的项目：优先补“多证据完整性”评测；只有单次补搜仍漏关键条件时，再增加循环深度。

用这个问题检验：同时问额度、审批人、生效日期，需要三项证据齐全；找到额度不意味着问题已回答。

08　答案、引用与拒答

场景示例关键机制项目适配判断失败风险如何验证

大库 / 高并发百万块资料、同时数十个问题近似索引 + 过滤 + 批处理 + 候选预算不能凭规模宣传判胜。所有系统需固定硬件、索引参数、模型服务和并发实测；纯检索与Agent分开。候选受限，ANN漏证据，重排服务排队。并发增长曲线、吞吐、P95/P99、质量变化和错误率。
场景决定路线：精确事实优先保证原文证据；表格聚合应考虑结构化工具；全库总结需要覆盖而不仅是相似；图关系需要消歧；无答案需要校准拒答。一个“总体正确率”会掩盖这些差异。

官方运行要求：Dify [10]；RAGFlow [7]；MaxKB [4]；QAnything [3]；GraphRAG [9]。其余比较为成本结构分析，不代表实测容量。

把三种时间分开

  1. 入库时间：解析 → OCR → 分块 → 生成上下文/图 → 向量化 → 可检索。
  2. 纯检索时间：查询向量 → 多路召回 → 融合 → 重排 → 来源组装。
  3. 端到端时间：再加路由、改写、充分性、补搜、首token和完整回答。

预计算把成本移到入库阶段；多步Agent把成本放到每次问答。二者不能混成一个“快慢”指标。

持续成本比首次启动更重要

总成本 = 计算与存储 + 模型索引/查询调用 + 数据同步 + 备份监控 + 人工知识维护 + 升级工程。

图谱、Wiki和多索引增加入库与更新成本；重排与多轮推理增加单次问答成本；纯CPU节省GPU预算但可能增加排队时间。

本报告不提供许可法律结论；正式商业选型还应单独核验实际版本许可与功能授权。

  • 每条查询的向量和关键词搜索当前依次调用；独立召回可考虑并行，但需评估模型/数据库负载。
  • 重排默认池12、最终最多6；父块扩展后实际token数不固定。可以同时记录token预算，避免固定条数带来上下文差异。

05 / WHAT “CORRECT” MEANS

正确率不是一个分数

召回

正确证据是否进入候选池？Recall@K；重排不能修复未召回的证据。

排序

正确证据排多前？MRR、nDCG、Precision@K；需要相关性标注。

完整性

多个条件和例外是否齐全？全部证据覆盖率，而不只是命中任一片段。

拒答

有答案是否误拒？无答案是否乱答？误拒率与误放率一起报告。

答案

结论、数值、单位和适用条件是否正确？参考答案加人工抽查。

引用

每项事实的来源是否支持它？编号合法只是第一层。

时效与权限

是否使用当前版本？是否越权？检查缓存与衍生知识。

成本下质量

相同模型、token预算、延迟目标下谁更好？画质量—成本曲线。

不要把分数当概率：sigmoid(logit)只保证数值在0～1并保持排序，未经校准的0.9不能解释成90%正确。召回率1.0也不能证明答案100%正确；它可能来自小样本、简单题或宽松证据匹配。

你已有池/重排/最终阶段分数及生成评审。建议补Precision@K或分级相关性标注，并以真实最终父块和线上充分性/补搜结果测证据覆盖。当前检索评分主要追踪候选子块，不能自动等同完整线上最终上下文质量。LLM评审应人工抽查，生成题目也需避免仅复述原文导致题目过易。

先测清楚，再增加模块

你的改进顺序

  1. 扩场景与难负例：从单份Markdown扩到真实PDF、表格、扫描件、政策例外和冲突版本。冻结holdout。
  2. 确认实际生效链路：记录模型模式、开关、阈值、召回深度、分块与token截断。
  3. 补语义引用与异常评测：逐主张支持度；重排超时、充分性格式异常、数据撤权。
  4. 分离三个预算：每路召回深度、重排候选数、最终token预算分别扫描。
  5. 按失败类型改进：解析差对照RAGFlow；双语匹配对照QAnything；多证据对照Agent；全局/关系题再试GraphRAG。
  6. 最后优化吞吐：召回并行、批处理、缓存与日志分级都要同时检查质量和权限。

公平对照的两条实验轨道

A / 检索机制比较：共用解析文本、分块和模型；固定候选/token预算，隔离融合、重排与图等方法差异。

B / 产品整体比较：同一批原始文件，允许各自解析器和推荐配置；明确不同模型/硬件，测质量与成本。

两种结果都必要：A回答“算法为什么更好”，B回答“直接使用产品是否划算”。不能拿B的优势全部归功于检索算法。
